# nba-quant 项目审查报告

- **审查对象**：`https://github.com/gem08166/nba-quant`（站点 `https://gem08166.github.io/nba-quant/`）
- **审查时间**：2026-11-04
- **审查版本**：仓库 HEAD `e9fd412`（`auto refresh: 2026-11-03`）
- **审查方式**：克隆仓库 + 实跑测试 + 实跑 walk-forward 回测 + 直查 SQLite + 抓取线上静态数据做一致性比对
- **审查环境**：Linux / Python 3.12

---

## 一、结论摘要

| 层面 | 判断 |
|---|---|
| 工程质量 | 27 个单元测试全通过；walk-forward 无未来函数；每请求独立 SQLite 连接 + WAL；PWA 可离线；Actions 定时刷新。个人项目里属偏上水平 |
| 模型层 | 可解释、无泄漏，但概率校准偏保守且分布失衡（ECE 0.0351，整体向 50% 压缩），开季误差明显劣化 |
| 定价执行层 | **问题集中区**：同书源重复计入、价格标签与真实可成交价不符、无后端分歧闸门、阈值低于噪声地板 |
| 验证层 | 让分样本 n=76 命中 59.2%，但 p=0.109 不显著，置信区间下限低于盈亏平衡线，**尚不能支撑“策略盈利”结论** |

一句话：**模型不是假的，但“模型 → 可下注 EV”这一段链路尚未校准好。**

## 二、线上与仓库不一致（优先处理）

本轮最关键的发现：**用户的最新改动没有生效到线上**。

| 检查项 | 线上 | 仓库 |
|---|---|---|
| `site/data/static.json` → `generated_at` | `2026-11-03T18:49:40Z` | `2026-11-03T19:22:44Z` |
| 回测报告是否含 `calibration` 字段 | 否 | 是（10 个分桶） |
| Service Worker 版本 | `nbaq-v11` | `nbaq-v12`（network-first） |

即页面展示的信号数（8 条）、最佳 EV（+30.8%）、ROI（+106.0%）与上一轮完全一致，原因不是“没改”，而是 **GitHub Pages 仍停留在 18:49 那一版数据**。

**建议动作**：检查 Actions 中 `deploy` job 的日志，确认是否 push 到 gh-pages、是否被 Pages 构建跳过（例如 `paths` 过滤、`deploy-pages` 权限缺失）。这是唯一一个“改了却看不见”的根因，优先级最高。

## 三、新增改动评估

### 3.1 校准诊断（`app/jobs/backtest.py:100 _calibration`）：方向正确，三处需修

实跑 841 场得到的可靠性曲线：

| 概率桶 | 预测均值 | 实际胜率 | gap | n |
|---|---|---|---|---|
| 0-10% | 0.078 | 0.200 | −0.122 | 5 |
| 10-20% | 0.157 | 0.103 | **+0.054** | 29 |
| 20-30% | 0.256 | 0.226 | +0.030 | 62 |
| 30-40% | 0.353 | 0.321 | +0.032 | 109 |
| 40-50% | 0.454 | 0.420 | +0.035 | 131 |
| 50-60% | 0.550 | 0.600 | **−0.050** | 155 |
| 60-70% | 0.647 | 0.693 | **−0.047** | 137 |
| 70-80% | 0.746 | 0.754 | −0.008 | 130 |
| 80-90% | 0.839 | 0.812 | +0.027 | 64 |
| 90-100% | 0.923 | 0.947 | −0.025 | 19 |

**加权 ECE = 0.0351（样本 841）**

形状解读：10–50% 区间系统性**高估**（弱队被高估 3–5.4pp），50–70% 区间系统性**低估**（强队被低估约 5pp）。等价于模型概率整体向 50% 压缩——这既解释了“最强信号来自弱队一侧”，也是为什么要做校准。

需要修正的三点：

1. **样本内自证**。曲线用同一批 841 场拟合，又用来解释同一批场次，必然好看。应切分为“前 600 场拟合 / 后 241 场验证”，在验证集上报告 ECE 才有决策意义。
2. **口径不匹配**。校准基于 `home_win_prob`（原始概率），信号里用的是 `MARKET_BLEND` 融合后的概率。融合本身就在把概率往 50% 拉，直接套曲线等于二次压缩。正确顺序是：先校准原始概率，再融合；或直接校准融合后的概率。
3. **只覆盖主胜**。让分（`cover_prob`）与大小分没有任何校准曲线，而这两类的 model_prob 同样直接进入 EV 计算。

### 3.2 用曲线重算今日 ML 信号（方向性估算）

| 比赛 | 方向 | 价格 | 模型概率 | 校准后 | 原 EV | 校准后 EV |
|---|---|---|---|---|---|---|
| PHI@DET | DET 主胜 | 1.85 | 0.662 | 0.702 | +22.5% | **+29.9%** |
| CHA@BKN | CHA 客胜(ML) | 1.74 | 0.668 | 0.706 | +16.3% | +22.9% |
| CLE@OKC | OKC 主胜 | 1.72 | 0.624 | 0.671 | +7.4% | +15.5% |
| MIN@HOU | MIN 客胜 | 4.01 | 0.326 | 0.295 | **+30.8%** | **+18.2%** |

结论：页面头条的「最佳 EV +30.8%」有近一半来自模型对弱队概率的高估，校准后降到 +18.2%；真正的头号信号应换成 DET 主胜。这与“分歧最大的信号最可能是模型错”的判断一致。

### 3.3 Service Worker 改动含致命语法错误

`site/static/sw.js` 中出现两次同名常量声明：

```js
// 第 1 行
const CACHE = "nbaq-v11";

// 第 33 行
const CACHE = "nbaq-v12";
```

`node --check` 报错：

```
SyntaxError: Identifier 'CACHE' has already been declared
```

后果：Service Worker 脚本解析失败 → **根本注册不上**。手机端不再有任何缓存（脏缓存问题“看似”解决），但离线能力与 PWA 安装同时失效。

**修法**：删除第 1 行起的旧定义组，只保留 v12 一份，保留 `skipWaiting` / `clients.claim`。

## 四、遗留未修问题

| # | 问题 | 证据 / 现状 |
|---|---|---|
| 1 | **同书源重复计入** | `odds_snapshots` 中 `Draft Kings` 24 条、`DraftKings` 30 条；`FanDuel` 30、`fanduel` 30。同一家书源两种写法被 `consensus_market` 当成两家，权重翻倍；且两条记录时间差可达 7 小时，旧价未剔除 |
| 2 | **价格标签谎报** | 信号 `book=Draft Kings`、`price=1.85`；实际 1.85 只有 FanDuel 有，Draft Kings 是 1.80。DET 主胜 EV 按真实价 1.80 重算为 +19.2%，而非 +22.5%（每条信号系统性高估约 3pp） |
| 3 | **分歧闸门未落地** | 仅前端 `app.js:345` 在 `divergence > 5` 时显示警告文案，后端生成信号时没有拦截 |
| 4 | **ATS 判定口径错配** | `backtest.py:68` 仍为 `model_home = home_prob >= 0.5`，而 `predict.py` 实际产出 `cover_prob`。对“模型看好赢 3 分、盘口 −8”的比赛两者方向相反 |
| 5 | **CLV 口径不完整** | `settle.py:108` 仍为 `bet["price"] / closing_price - 1`，丢失让分线移动的价值 |
| 6 | **σ 为样本内残差** | `sigma_margin 14.505` vs 样本外 RMSE `15.21`（低估 4.6%）；`sigma_total 18.877` vs `19.15`（低估 1.4%） |
| 7 | **开季退化** | 分差 MAE：2026-10 为 13.26，2026-03 为 11.40（+16%）。印证 `half_life_days=120` 跨休赛期（约 150 天）时上季权重仍 0.42 |
| 8 | **单边报价出假信号** | `fair_two_way` 缺一边时返回 0.5/0.5，`_make_edge` 仍照常产出 edge |
| 9 | **整数盘口 6/122** | `cover_prob` 用 `floor(-line)+0.5`，`settle` 有 push 分支，定价与结算口径不统一 |
| 10 | **`latest_odds` 用 `ORDER BY id`** | 实测存在 `captured_at` 逆序，可能取到旧价 |
| 11 | **演示注单污染头条** | `bets` 表唯一一条为 `game_id 401909907, model_prob=0.5, ev=0.0, price=2.06, result=won, clv=0.03, profit=1.06`，却渲染成“1 结算 · ROI +106.0% · CLV +3.0%” |
| 12 | **“无盘口”显示成“无信号”** | `app.js:80/:129`，14 场中 8 场实为无盘口报价 |
| 13 | **信号计数按“边”不按“场”** | 8 条边实际只涉及 4 场 |
| 14 | **静态刷新延迟** | 数据走 GitHub Actions 每 2 小时一次（UTC 02/08 = 北京 10:00/16:00），文班伤停这类突发无法及时反映（SW 本意是解决该问题，但见 3.3） |
| 15 | **时区近似** | `dates.py` 固定 `UTC-5` 处理美东日期，夏令时期间存在 `04:00–05:00Z` 窗口的日期偏移（影响极小，代码注释已承认） |
